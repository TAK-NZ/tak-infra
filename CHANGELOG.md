## Version History

### Pending Release
- :tada: Certificate metrics and alarms (#129). New `cert-metrics.sh` (`emit`, or `emit_metric` when sourced) writes to the CloudWatch namespace `TAK/Certificates` with a `Stack` dimension, refuses unknown metric names and never fails its caller. With `pki.kmsCa` enabled the stack creates the 13 alarms of #129 (expiry warnings, rotation events and failures, rotation phases, coverage stragglers, expired CA) and three SNS topics (alert, critical, info; optional `pki.kmsCa.alertEmail` and `infoEmail`). The Root CA signing alert of #136 now publishes to the alert topic. The container runs `check-expiry` 60 seconds after the start and every 24 hours: it emits 0 or 1 for `RootCAExpiryWarning` (730 days), `IntermediateCAExpiryWarning` (1275 days) and `CAExpired` from the CA certificates of a stack with the first-boot PKI. The alarms for rotation events stay in OK until #130, #131, #132, #135, #169, #171 and #172 emit their metrics. Tests: `test/KmsCa/test-cert-metrics.sh` (47 checks, in CI) and unit tests.
- :tada: First-boot PKI for new stacks (#189). With `pki.kmsCa` enabled, `start-tak.sh` runs the new `pki-bootstrap.sh` before the TAK Server certificate scripts. On a stack with no PKI it builds Root CA 01 and Intermediate CA 01 in KMS (via `kms-ca.sh`), an Enrollment CA 01 with a software key, the server certificate (CN `<servicename>.<zone>`, SAN `takserver`, `<servicename>.<zone>`, `<hostname>.<zone>`), the admin certificate, and the keystores and truststores TAK Server expects. No CA key is written to the EFS: the Enrollment CA key lives in a retained Secrets Manager secret and is restored into tmpfs on every start (the file TAK Server reads is a symlink). The server truststore holds Root CA, Intermediate CA and Enrollment CA; the new `truststore-phone.p12` holds only Intermediate CA and Root CA. `admin.pem` and `admin.key` are written too, because the container health check reads them. A stack that already has a PKI is left alone; with the state file present a missing file or secret stops the start. New settings `pki.kmsCa.validity.*` (default 20 y / 10 y / 3 y / 1 y / 1 y) and `pki.kmsCa.p12Profile` (default `compat3des`), command line `pkiRootDays` and so on, validated at synth. No renewal or rotation yet (#131, #132, #135, #169, #171, #172). Tests: `test/KmsCa/test-pki-bootstrap.sh` (100 checks with SoftHSM, in CI) and unit tests. Not yet run in ECS.
- :tada: Root CA and Intermediate CA signing keys in AWS KMS (#136). New optional `pki.kmsCa` setting (off by default, nothing changes for existing stacks; command line `pkiKmsCaEnabled`, `pkiEnvironmentLabel`, `pkiRootCaNumbers`, `pkiIntermediateCaNumbers`, `pkiAlertEmail`) creates one RSA-4096 KMS key per Root CA and Intermediate CA generation (aliases `alias/tak-nz-<env>-root-ca-01`, `alias/tak-nz-<env>-intermediate-ca-01`, retained on stack deletion) and passes them to the container as `PKI_KMS_CA_KEYS`. The key policy lets only the TAK Server task role sign (everyone else, including administrators, is denied `kms:Sign`), and every use of a Root CA key publishes to an SNS topic through an EventBridge rule on the CloudTrail `Sign` event. That event is read-only, so the rule uses state `ENABLED_WITH_ALL_CLOUDTRAIL_MANAGEMENT_EVENTS` and needs a CloudTrail trail that logs management events; this stack does not create one (BaseInfra does, base-infra#101; accounts that already have a trail opt out with `createCloudTrail=false`). Checked in a throwaway stack (deployed, then destroyed; account 814704514736, ap-southeast-2): an IAM user is denied `kms:Sign` on both keys, the signer role signs through `kms-ca.sh` (root, intermediate, server certificate, CRL), and each Root CA signature reached an SNS-to-SQS subscription within about 10 seconds. Then checked on a deployed dev-test stack (account 814704514736, ap-southeast-6, stack `Demo`, label `Dev`): in the running TAK Server task (ECS Exec, task role credentials from the container endpoint) `kms-ca.sh` signed a root, an intermediate, a server certificate and a CRL with real KMS keys, and the two Root CA signatures raised exactly two alerts (EventBridge TriggeredRules 2, SNS published 2). Not tested: the alert without a CloudTrail trail. A denied attempt does not raise the alert, because the denied event carries no key ARN.
- :tada: The TAK Server image (`Dockerfile.tak-nz` and `Dockerfile.generic`) now contains the `aws-kms-pkcs11` v0.0.19 module (pinned, SHA-256 checked at build time) and the libp11 OpenSSL engine, and a new `kms-ca.sh` wrapper (`csr`, `root-self-sign`, `issue-ca`, `sign`, `crl`) that signs CA certificates, server certificates and CRLs with a named KMS key. Path length defaults leave room for the Intermediate CA bridge (Root CA 3, Intermediate CA 2, bridged Intermediate CA 1 via an optional `issue-ca` argument, Enrollment CA 0). Unlike `makeCert.sh` it never falls back to a default key, uses a positive 64-bit serial, and checks every result against the issuer certificate. Nothing calls it yet: first-boot use is #189. See `docs/KMS_CA_KEYS.md`.

- :bug: Assign the TAK logo to the WebTAK application in Authentik. The `TAK-WebTAK` application was created with an empty icon: the setup Lambda read `url` from the response of `POST /api/v3/admin/file/`, but Authentik 2026.8 returns an empty body from that endpoint (the Lambda logged `Could not find url field in upload response`), so `meta_icon` was never set. The Lambda now uploads `tak-logo.png` under the stable name `application-icons/tak-logo.png`, treats `400 ... already exists` as success (the upload is not idempotent) and sets `meta_icon` to that name, the same calls the TAK Team Manager Lambda uses. An icon that is already set is left alone, and the Lambda runs on every deploy, so redeploying the TakInfra stack fixes an existing application. Checked with a stub that mimics the 2026.8 upload behaviour (icon empty before, set after, repeat runs safe); not tested against a real Authentik.
- :bug: Set `grant_types` (`authorization_code`, `implicit`, `hybrid`) on the WebTAK OIDC provider in Authentik. The setup Lambda omitted the field, Authentik 2026.8 then stores an empty list, and a provider with no grant types rejects every authorize request: Authentik logs `Invalid grant_type for provider: authorization_code` and redirects back to TAK Server with `error=invalid_request` ("The request is otherwise malformed"), so logging in at `https://ops.<domain>` fails. Found on a new deployment (Auckland, ap-southeast-6); an existing environment whose provider was created before Authentik had `grant_types` is not affected. Redeploying the TakInfra stack repairs an existing provider, because the Lambda runs on every deploy and updates the provider with PATCH. The TAK Team Manager Lambda already set the same values (TAKTeamManager 76b0fa2). Checked with a stubbed Authentik API: the PATCH payload had no `grant_types` before and has all three now; not tested against a real Authentik.
- :bug: TAK Server could not start on a new database. The schema migrations (V7 onwards) call PostGIS functions such as `AddGeometryColumn` but nothing installed PostGIS, so `SchemaManager upgrade` failed with `function addgeometrycolumn(...) does not exist` and the ECS circuit breaker rolled the stack back. Existing environments were unaffected because their databases already had PostGIS. `start-tak.sh` now installs the extensions with `psql` (`CREATE EXTENSION IF NOT EXISTS postgis`, then `fuzzystrmatch`, `postgis_tiger_geocoder` and `postgis_topology` best effort) while `SchemaManager validate` reports the database is not initialized. It is idempotent, and a PostGIS failure stops the task with a clear message. `SchemaManager SetupRds` (the first fix, #183) does not work on Aurora PostgreSQL 18: it sends all its statements as one batch, and `alter schema tiger owner to rds_superuser` is rejected (`cannot alter ownership to "rds_superuser"`), which rolled back `create extension postgis` with it. Found on the first deploy to a new Aurora cluster (Auckland, ap-southeast-6). Verified against local Postgres with the real `SchemaManager.jar`; not yet verified on Aurora.

- :rocket: TAK-GPT plugin: new optional bot setting `knowledgeBaseResults` (used together with `knowledgeBaseId`, or `knowledgeBaseIds` for an agent with several knowledge bases, in agent mode) sets how many chunks the agent retrieves per knowledge base search, sent as `numberOfResults` in the `InvokeAgent` session state on every call of a RETURN_CONTROL loop. - :tada: Bedrock Knowledge Bases move into CDK on Amazon S3 Vectors (#158). New `BedrockKnowledgeBase` construct creates, per name in the new `bedrock.knowledgeBases` setting (default `["nema-cdem"]`; override `--context bedrockKnowledgeBases=nema-cdem,nzdf`): a vector bucket and index (1024 dimensions, float32, cosine), the service role (reads only `bedrock-kb/<name>/` in the TAK Images bucket, decrypts with its key, invokes Titan Embed Text v2, and uses only its own index), the knowledge base `<name>-s3v` and its S3 data source. IDs are stack outputs (`BedrockKb<Name>Id`, `BedrockKb<Name>DataSourceId`). It replaces the OpenSearch Serverless collection that the setup script created: that collection billed about $340 (Test) and $400 (Demo) a month around the clock for almost no search traffic. Spikes in Test: retrieval 0.35 s with no cold start (NextGen OpenSearch with minimum 0 OCU had an 11 to 14 s first query), and the same number of answer-key facts in the retrieved chunks as the current knowledge base (63 against 65 of 282 on the 37 benchmark questions; within noise). Nothing changes for a running environment until the stack is deployed and the setup script is run; the old collection keeps billing until it is deleted (steps in `scripts/bedrock/README.md`). Not yet verified: answer quality through the agent, and Demo's own knowledge bases.

Knowledge bases with other names stay attached, and `--extra-kb-name` attaches more than one (the Demo NZDF SENTINEL agent uses `nzdf` and `nema-cdem`). - :rocket: Database construct: set `log_statement` to `ddl` (was `all`). The TAK Server database wrote about 2 MB/s of PostgreSQL log (170 to 225 GB a day, a new 100 MB file every ~50 s) because every CoT message is an `INSERT INTO cot_router` that `all` logs together with its parameters (callsigns, positions). That log load costs CPU and local storage on the provisioned `db.t4g.large`, which has no CPU credit headroom. The log was never exported (`enableCloudWatchLogs` is off) and is kept 3 days locally. Schema changes are still logged, and statements over 1 s are still logged through `log_min_duration_statement`. The parameter is dynamic, so there is no reboot. Applies to every cluster this construct creates, including `prod`. To debug a query problem, set `log_statement` back to `all` or `mod` on the cluster parameter group for a short time.
