# Root CA and Intermediate CA keys in AWS KMS

Tracked in [#136](https://github.com/TAK-NZ/tak-infra/issues/136), part of the certificate rotation epic [#128](https://github.com/TAK-NZ/tak-infra/issues/128). The target PKI is described in [#171](https://github.com/TAK-NZ/tak-infra/issues/171).

New stacks keep the private keys of the Root CA (R) and the Intermediate CA (S) in AWS KMS. They never exist as files on EFS, in container memory or in Secrets Manager. The Enrollment Signing CA (Cl) is not in KMS: TAK Server signs client certificates in-process from a keystore.

This page covers the keys, how the container signs with them, and how to operate them. On a new stack the first boot builds the PKI with these keys (`pki-bootstrap.sh`, [#189](https://github.com/TAK-NZ/tak-infra/issues/189), see below). Renewal and rotation come later ([#131](https://github.com/TAK-NZ/tak-infra/issues/131), [#132](https://github.com/TAK-NZ/tak-infra/issues/132), [#135](https://github.com/TAK-NZ/tak-infra/issues/135), [#169](https://github.com/TAK-NZ/tak-infra/issues/169), [#171](https://github.com/TAK-NZ/tak-infra/issues/171), [#172](https://github.com/TAK-NZ/tak-infra/issues/172)).

## Turning it on

Off by default. A stack that does not set it is unchanged.

```json
"pki": {
  "kmsCa": {
    "enabled": true,
    "environmentLabel": "Try",
    "alertEmail": "pki-alerts@example.org"
  }
}
```

or on the command line: `--context pkiKmsCaEnabled=true --context pkiEnvironmentLabel=Try`. See [PARAMETERS.md](PARAMETERS.md#kms-ca-keys).

## What the stack creates

| Resource | Details |
|---|---|
| One KMS key per Root CA and Intermediate CA generation | RSA-4096, `SIGN_VERIFY`, alias `alias/tak-nz-<env>-root-ca-01` and `alias/tak-nz-<env>-intermediate-ca-01`. `RETAIN`: CloudFormation never deletes them |
| Key policy | The account root has management actions only (no `kms:Sign`). The TAK Server task role may `kms:Sign`, `kms:GetPublicKey` and `kms:DescribeKey`. Everyone else, including administrators and the account root, is denied `kms:Sign` |
| SNS topic and EventBridge rule | An alert on every `kms:Sign` that uses a Root CA key. Optional email subscription |
| Container variables | `PKI_ENV_LABEL`, `PKI_KMS_CA_KEYS` (`root-ca-01=<key id>,intermediate-ca-01=<key id>`), `PKI_KMS_REGION` |
| Stack outputs | `RootCa01KeyId`, `IntermediateCa01KeyId`, ... |

KMS never exports the private key of an asymmetric key, so the key policy has no export statement.

The task role is the only signer. The Root CA and Intermediate CA steps run in the same task, so IAM cannot allow Root CA signing for some steps and not for others: the alert on every Root CA signature covers that.

### Root CA signing alert needs a CloudTrail trail

`kms:Sign` is a **read-only management event**. EventBridge only sees it when the account has a CloudTrail trail that logs management events (read and write) in the Region of the stack, and the rule has state `ENABLED_WITH_ALL_CLOUDTRAIL_MANAGEMENT_EVENTS` (the construct sets this). This stack does not create the trail: BaseInfra does (setting `cloudTrail.enabled`, default `true`, [base-infra#101](https://github.com/TAK-NZ/base-infra/issues/101)). An account that already has a trail that logs read events in this Region (for example 814704514736 and 453572736517) deploys BaseInfra with `--context createCloudTrail=false`. Check with `aws cloudtrail get-event-selectors --trail-name <trail>` that `ReadWriteType` is `All`. Without such a trail the keys and the signing still work, but no alert is sent. Every call is also visible in CloudTrail event history within seconds.

## Names

Defined in #171. The number identifies a key, not a certificate.

| | Example |
|---|---|
| CN (display name, with `O=TAK.NZ`) | `TAK.NZ Try Root CA 01`, `TAK.NZ Try Intermediate CA 01` |
| KMS alias | `alias/tak-nz-try-root-ca-01` |
| PKCS#11 token label and key label | `root-ca-01`, `intermediate-ca-01` |

To start a rotation, add the next number (`rootCaNumbers: [1, 2]` or `intermediateCaNumbers: [1, 2]`) and deploy. The new key gets the next name; the old key stays.

## Signing in the container

`/opt/tak/scripts/kms-ca.sh` signs with OpenSSL through the `pkcs11` engine (libp11) and the [`aws-kms-pkcs11`](https://github.com/JackOfMostTrades/aws-kms-pkcs11) module, which calls `kms:Sign` with the task role. Both are installed in the TAK Server image (pinned release, checksum checked at build time). Unlike TAK's `makeCert.sh`, which always signs with `ca.pem` and `ca-do-not-share.key`, every command names the signing key.

| Command | Purpose |
|---|---|
| `kms-ca.sh config` | Write the module config from `PKI_KMS_CA_KEYS`. The other commands do this themselves |
| `kms-ca.sh csr <label> <out.csr>` | CSR for a KMS key, subject from the naming rules |
| `kms-ca.sh root-self-sign <root-label> <out.pem> <days>` | Self-signed Root CA certificate (pathlen 3) |
| `kms-ca.sh issue-ca <issuer-label> <issuer.pem> <in.csr> <out.pem> <days> [pathlen]` | CA certificate: root issues an Intermediate CA (pathlen 2), intermediate issues an Enrollment Signing CA (pathlen 0). Pass `[pathlen]` 1 for a bridged Intermediate CA certificate (#172). Signing the CSR of an existing key with another root is the cross-certification of #169 |
| `kms-ca.sh sign <issuer-label> <issuer.pem> <in.csr> <out.pem> <days> <ext-section> <ext-file>` | Server or client certificate, same `-extensions`/`-extfile` handling as `makeCert.sh` |
| `kms-ca.sh crl <label> <cert.pem> <out.crl> <days>` | CRL signed by a KMS key (`makeCert.sh` makes one for every CA it creates) |

The path length defaults leave room for the Intermediate CA bridge of #172 (`R -> S_old -> S_new(A) -> Cl -> client`): Root CA 3, Intermediate CA 2, bridged Intermediate CA 1, Enrollment CA 0. With smaller values a strict validator rejects client certs issued below a bridged certificate (`path length constraint exceeded`; found while testing #133).

Every command checks its result against the issuer certificate and deletes the output if the KMS key is not the key of that certificate.

Notes from the #134 spike:

- `openssl x509 -req` does not copy CSR extensions, so an extension file is always needed.
- Signing takes about 1.2 s per `openssl` process (module start-up fetches the public key of every configured key). The account quota is 1000 RSA operations per second.
- The module config lists only the keys in `PKI_KMS_CA_KEYS`.

## First boot of a new stack (`pki-bootstrap.sh`)

`start-tak.sh` runs `/opt/tak/scripts/pki-bootstrap.sh` before it looks at the TAK Server certificate scripts. With `pki.kmsCa` enabled and no PKI on the EFS yet it builds, in this order:

| Step | Result |
|---|---|
| Root CA 01 | self-signed in KMS, 20 years, pathlen 3 |
| Intermediate CA 01 | issued by Root CA 01 in KMS, 10 years, pathlen 2 |
| Enrollment CA 01 | software key, issued by Intermediate CA 01, 3 years, pathlen 0 |
| Server certificate | CN `<servicename>.<zone>`, SAN `takserver`, `<servicename>.<zone>`, `<hostname>.<zone>`, issued by Intermediate CA 01, 1 year |
| Admin certificate | issued by Enrollment CA 01, 1 year |

Names follow the rules above (`TAK.NZ <Env> <Tier> NN`); the host names come from `takserver.servicename`, `takserver.hostname` and the hosted zone, never from a literal. Every CA certificate has a key-id based Authority Key Identifier.

Files in `/opt/tak/certs/files`, with the names TAK Server and the other scripts already use: `takserver.jks/.p12/.pem/.key`, `admin.p12/.pem/.key`, `truststore-intermediate-ca.jks/.p12`, `fed-truststore.jks`, `ca.pem` (the issuing Intermediate CA), `root-ca.pem`, `intermediate-ca.pem`, `enrollment-ca.pem`, `pki-state.json` and, new, `truststore-phone.jks/.p12`.

- **Server truststore** holds Root CA, Intermediate CA and the Enrollment CA: TAK Server must trust the issuer of every client cert, because ATAK sends only its leaf cert (#133).
- **Phone truststore** (`truststore-phone.p12`, use it for data packages) holds only Intermediate CA and Root CA. A phone does not need the Enrollment CA, and keeping it out of phone stores avoids the known limit in #171. `truststore-root.p12` is not created: a phone with only the root cannot validate the server cert (#170).
- **The Enrollment CA key** is generated in tmpfs and written only to the secret `<stack>/...Enrollment-CA` (a retained Secrets Manager secret, PKCS#12 with the key and the chain). The file TAK Server reads, `intermediate-ca-signing.jks`, is a symlink into tmpfs, restored from the secret at every start. No CA key is on the EFS: there is no `root-ca-do-not-share.key` and no `ca-do-not-share.key`.
- **Admin cert files:** `admin.p12` for the services that call the TAK API, and `admin.pem` / `admin.key`, which the container health check reads (#189 finding from #133).
- **Keystore password** stays `atakatak`, the value `CoreConfig.xml` uses for every keystore. It protects the JKS and PKCS#12 files only: R and S are in KMS and the Enrollment CA key is in Secrets Manager.
- **PKCS#12 profile** of the user-facing p12 files (`takserver.p12`, `admin.p12`): `P12_PROFILE`, `compat3des` by default (3DES, SHA-1 MAC; plain `-legacy` is never used).
- **Not touched:** a stack that already has a PKI from the old scripts (`ca.pem` without `pki-state.json`) keeps it. There is no migration.
- **Fails closed:** with `pki-state.json` present, a missing file or an unreadable secret stops the start instead of generating a second PKI. A failed write to Secrets Manager installs nothing, so the next start can bootstrap again.
- **Several nodes:** `pki-bootstrap.sh` runs under the cluster lock (`docs/CLUSTER_LOCK.md`). On a fresh stack one node builds the PKI, the others wait and restore it. The decision between build, restore and "old flow" is made inside the lock.
- **Not in this step:** renewal and rotation, the CRLs and revocation scripts of the old flow.

`pki-state.json` records the names, the p12 profile and the expiry dates, for the rotation orchestrator (#171).

## Server certificate rotation (`server-cert-rotate.sh`)
The TAK Server certificate (`takserver.pem`, `.key`, `.p12`, `.jks`) is rotated automatically on stacks with the first-boot PKI ([#131](https://github.com/TAK-NZ/tak-infra/issues/131)). A loop in `start-tak.sh` runs `server-cert-rotate.sh check` 15 minutes after the start and then every 24 hours; it rotates when the certificate has `pki.kmsCa.validity.serverCertRenewDays` (default 60) or fewer days left. `server-cert-rotate.sh rotate` rotates at once. Stacks with the PKI of the TAK Server scripts are left alone.
Rotation runs under the cluster lock `server-cert-rotation`, so one node does it (`docs/CLUSTER_LOCK.md`):
1. A new key and CSR for the names in `PKI_SERVER_NAMES` (so a changed host name or service name is picked up), signed by Intermediate CA S in KMS. Validity `serverCertDays` (default 365).
2. Everything is built and checked in tmpfs first: chain to R and S, key against certificate, CN and SAN, days left, and that the new `takserver.jks` and `takserver.p12` open with the keystore password and hold the new certificate. A failed check changes nothing on the EFS.
3. Swap: a marker file, a `.prev` copy of each of the four files, one atomic rename per file, the same checks on the installed files. A failure restores the `.prev` copies. A marker found at the next run means the swap was interrupted (task stopped): the `.prev` copies are restored then, and nothing is rotated until that works.
4. The state file gets the new `notAfter.server`, `TakServerCertRotated` is emitted, and an ECS rolling deployment makes every node load the new keystore (TAK Server reads it at start). Phones are not touched: they do not pin the leaf, and S and R are unchanged.
Every failure emits `TakServerCertRotationFailed` (alert). If only the deployment cannot be started, the new certificate stays installed and the failure metric tells you that TAK Server loads it at its next restart. `takserver.pem.prev` and the other `.prev` files hold the last previous set (the key and p12 are mode 600); the next rotation overwrites them. The renewal threshold must be smaller than the validity (checked at synth and at run time), or each new certificate would be rotated again at once.
Not covered: the admin certificate (#132), and a server certificate signed with a different Intermediate CA than the one in the state file (#172).
## Truststores and signing keystore (`pki-trust-lib.sh`, `pki-trust.sh`)
What TAK Server trusts and what it signs enrolments with is changed in one place, for the rotation scenarios of the orchestrator (#171, slice B). `pki-bootstrap.sh` uses it too, so there is one code path.
- **Manifest.** `pki-state.json` has `.trust.entries`: alias, file and the sets of each CA certificate. Sets: `server` (`truststore-intermediate-ca.jks/.p12`: R, S and every live Enrollment CA, because ATAK sends only its leaf certificate, #133), `phone` (`truststore-phone.jks/.p12`: S and R, what data packages carry) and `fed` (`fed-truststore.jks`: S and R). A PKI that was built before the manifest existed gets the default one at the first use.
- **`pki-trust.sh add <alias> <pem> <sets>`** puts a CA certificate into the manifest. It must be a CA certificate and chain to the Root CA through the Intermediate CA, so a wrong file cannot be added by mistake. The file is kept in `trust-certs/<alias>.pem`. `remove <alias>` takes an entry out. Neither changes the truststores.
- **`pki-trust.sh apply`** rebuilds the five files from the manifest in tmpfs, compares them with what is installed (alias and SHA-256 fingerprint of every entry), and does nothing when they are equal (exit 0). Otherwise it swaps them in with a marker, `.prev` copies and one rename per file, checks the installed files, and returns 10: **TAK Server reads its truststore only at start, so a change needs a restart**; the orchestrator then starts one rolling deployment. A failure restores the `.prev` copies (exit 1); an interrupted swap is restored by the next `apply`; a set that would be empty, or a missing certificate file, is refused.
- **The chain above Cl.** `enrollment-chain.pem` (public, on the EFS) holds the certificates above the Enrollment CA up to R, in order: [S, R] normally, [A, S_old, R] during the bridge of an Intermediate CA rotation (#172). The signing keystore of a new Enrollment CA and the admin certificate (`admin.pem` without R, `admin.p12` with it) are built from it. A PKI from before the file gets [S, R] at its next start.
- **Signing keystore generations.** The Enrollment CA key is a software key in a Secrets Manager secret. Generation 1 is the secret that CDK creates. `pki-trust.sh install-signing <N> <p12>` stores generation N as `<StackName>/TAK-Server/Enrollment-CA-NN` (**created at run time**: the task role may create, describe, read and write secrets with exactly that prefix, nothing else; it may delete one only with a recovery window of 30 days or more), reads it back, makes it the current one (`.enrollmentSecret` and `.numbers.enrollment` in `pki-state.json`) and puts it into this node's tmpfs. A node that starts later restores the current generation (`pki-bootstrap.sh`). An existing secret with another keystore is never overwritten. `pki-trust.sh rechain-signing <N> <p12>` writes a new version of an existing generation secret with another chain above Cl (same key and certificate, checked), for the cut of an Intermediate CA rotation (#172); it updates this node's tmpfs when N is the current generation. Deleting the old secret is the retire step of the Enrollment CA rotation (#135, `pki-trust.sh retire-signing <N>`, below).
- All changes take the cluster lock `pki-rotation`, the orchestrator's.
Another node keeps the old signing keystore in its tmpfs until it restarts. Its admin certificate rotation then refuses to sign (it checks that the key matches `enrollment-ca.pem`); the rolling deployment that follows a Cl switch replaces it.
## Revoking a certificate (`revoke-cert.sh`, `pki-crl-lib.sh`)
TAK Server finds the administrator by the CN of any certificate that its truststore accepts, so the old admin certificate of a rotation keeps working until it expires, and the revoke API of TAK Server (certadmin) knows only certificates that TAK Server issued itself. A **CRL per Enrollment CA** closes that gap ([#204](https://github.com/TAK-NZ/tak-infra/issues/204)). Checked on the dev-test stack (TAK Server 5.8): a certificate that is in the CRL is refused on 8089 (`alert certificate revoked`) and on 8443 (no connection), while another valid certificate with the same CN (the real admin certificate) keeps working; an empty CRL changes nothing for anyone; **TAK Server reads CRL files only at start** (a changed file was not picked up in 12 minutes), so a revocation needs a rolling deployment (4 to 9 minutes, the old task serves until the new one is healthy); **`nextUpdate` is not enforced** (an expired CRL keeps revoking and blocks nobody, also after a restart), so there is no alarm for an expiring CRL.
- **Files.** `/opt/tak/certs/files/crl/<alias>.crl` (PEM, public, valid 365 days, `pki.kmsCa`-independent setting `PKI_CRL_DAYS`) and the `openssl ca` database in `crl/db/<alias>/` (index and serial numbers, no key). `pki-bootstrap.sh` creates an empty CRL for Enrollment CA 01 at the first boot, and every later start creates the missing CRL of every Enrollment CA in the trust manifest, before `CoreConfig.xml` is generated. `createCoreConfig.sh` adds one `<crl _name crlFile>` to `<security><tls>` for every `crl/*.crl` (all templates, valid against the CoreConfig.xsd of TAK Server). **The database holds the list of revoked certificates**: it lives on the EFS like the rest of the PKI state; if `crl/` is lost, revoked certificates are valid again until they are revoked again.
- **The combined file `crl/00-all.crl`.** Found on the dev-test stack while testing #135: **the API of TAK Server (port 8443) honours only the first `<crl>` element**. With a CRL for Enrollment CA 02 listed second, every certificate from CA 02, the admin certificate included, was refused on 8443 ("certificate unknown": the revocation status of its issuer is undetermined), while 8089 (messaging) accepted it. A file that holds the CRLs of all Enrollment CAs one after the other (PEM) is read completely (checked: with it first, a certificate from CA 02 is accepted on 8443). So `00-all.crl` is rewritten after every change of a CRL and at every start, and `createCoreConfig.sh` lists it first (the glob sorts it before `enrollment-ca-NN.crl`); the files of the single CAs are still listed after it.
- **Signing.** The CRL is signed with the key of the Enrollment CA that issued the certificate: the current generation from tmpfs, an older one from its secret (`<stack>/TAK-Server/Enrollment-CA-NN`, generation 1: the secret of the stack). The key is in a temporary tmpfs file for the time of the signing. A new CRL is checked (signature, serial listed) before it replaces the old one; a failure puts the database back.
- **`revoke-cert.sh <cert.pem> [--reason R] [--no-restart]`** revokes a certificate by serial in the CRL of its issuer (and only that certificate). **`--serial HEX --ca enrollment-ca-NN --subject /O=TAK.NZ/CN=name --not-after DATE`** does it for a certificate that is not at hand (serial from a log). `--list` shows what is revoked. Unless `--no-restart` is given it starts the rolling deployment; it emits `CertificateRevoked` (alert). Reasons: `unspecified` (default), `keyCompromise`, `CACompromise`, `affiliationChanged`, `superseded`, `cessationOfOperation`, `certificateHold`. Emergency for a leaked admin or user key: `revoke-cert.sh admin.pem.prev --reason keyCompromise`, or by serial.
- **The admin certificate rotation** (#132) revokes the previous admin certificate when its grace period ends (reason `superseded`), starts the rolling deployment, and only then deletes the copies of the old key; a failed revocation keeps the copies and tries again at the next run. A previous certificate that expired anyway is skipped.
- **Not covered:** the federation ports (their `<tls>` element is separate and has no CRL) and port 8446 (`clientAuth="false"`); whether TAK Server checks the signature of a CRL was not tested.
## Rotation orchestrator (`pki-rotate.sh`)
One entry point for every rotation of the PKI ([#171](https://github.com/TAK-NZ/tak-infra/issues/171)). The loop in `start-tak.sh` calls `pki-rotate.sh run` 15 minutes after the start and then every 24 hours, on stacks with the first-boot PKI. `run` does, in this order: the admin certificate check (`admin-cert-rotate.sh`, #132), the server certificate check (`server-cert-rotate.sh`, #131; last, because its rotation ends in a rolling deployment), then the orchestrated rotations of the CAs, then the checks behind the alarms.
**The CA rotations are scenarios** (a file `rotation/<name>.sh` with the functions listed in the header of `pki-rotate.sh`): an ordered list of steps with gates between them, kept in `/opt/tak/certs/files/rotation-state.json` (active rotation, step, times, history) so that a rotation that takes more than a year survives restarts, crashes and node changes. The Enrollment CA (#135, below), the Intermediate CA (#172, below) and the Root CA (#169) are scenarios; `plan` shows a layer whose scenario is not built yet as such.
Gates (all must be open for a step to run):
| Gate | Opens when |
|---|---|
| `restart` | TAK Server runs in a task that started after the previous step (that step asked for a restart, and the rolling deployment has replaced the task). A rotation that waits for this for more than two days counts as stuck (`RotationWaiting`): the deployment failed |
| `window` | W has passed since the previous step: W = client certificate validity + buffer = 365 + 90 = 455 days (`pki.kmsCa.rotation.clientCertDays` and `bufferDays`). Every phone has got a certificate from the new chain by then |
| `coverage` | `rotation-coverage.sh` reports no active user who is still on the old side (below). While it does, the list of users goes to the log and to the alert topic and `RotationCoverageStragglers` carries the number |
| `approval` | `pki-rotate.sh approve <scenario> <step>`. Required for the steps in `pki.kmsCa.rotation.requireApproval` (default `cut` and `retire`, the steps that cannot be undone); an empty list switches approvals off |
A step can have a hard deadline (what it depends on expires, minus a margin). From then on the window and the coverage gate are open. The approval is never skipped. Steps are idempotent: after a crash the step that was running runs again. A step that fails is retried at the next daily run (`RotationStepFailed`). A step that needs TAK Server to reload its truststore or signing keystore asks for a restart; the orchestrator starts one rolling deployment after it has saved its state.
Commands: `pki-rotate.sh plan [--at DATE] [--json]` prints every layer with its expiry, the date its rotation triggers and whether it is due, the spare key generations, and the active rotation with the day its next window opens. It changes nothing and `--at` shows the future (a dry run of the whole lifecycle). `status` prints the state file and what the rotation waits for. `approve` and `abort` as above.
Triggers (all configurable, `docs/PARAMETERS.md`): server and admin certificate at 60 days or fewer left; Enrollment CA at an age of 365 days (`enrollmentCaRotationDays`); Intermediate CA at expiry - (2 x W + 365 days); Root CA at expiry - (W + 365 days). The settings are checked when the stack is synthesized: an Enrollment CA must live for its rotation period plus W, an Intermediate CA for 2 x W + 365 days, a Root CA for W + 365 days.
**Spare key generations.** KMS keys are created by CDK, not by the container: a task role that could create keys and change key policies would weaken the one thing the key policies protect. So that no operator has to act under pressure, generation 2 of the Root CA and of the Intermediate CA is created together with generation 1 (`rootCaNumbers` and `intermediateCaNumbers` default to `[1, 2]`; a key costs about US$1 a month, and only the signer role can use it). When a rotation has used the spare, `run` emits `RotationSpareKeyMissing` (`Tier=root` or `intermediate`, alert) every day until the next number is added to the configuration and deployed. That is years before the next rotation is due, and the message in the log says what to change.
Alarms (#129): `RotationStepFailed`, `RotationWaiting` (a rotation waits for an approval or for the coverage check although its window is over), `RotationSpareKeyMissing`.
## Intermediate CA rotation (`rotation/intermediate.sh`)
The second scenario of the orchestrator ([#172](https://github.com/TAK-NZ/tak-infra/issues/172)). The Intermediate CA (S) signs the server certificate and the Enrollment CAs. ATAK ignores the chain that the server sends ([#170](https://github.com/TAK-NZ/tak-infra/issues/170)), so the issuer of the server certificate must already be in the truststore of every phone before the server uses it. A phone holds `{S_old, R}`, or after an enrolment during the bridge `{A, S_old, R}`. **A** is the certificate for the S_new key issued by S_old (pathlen 1), **B** the certificate for the same key and subject issued by R (pathlen 2): a phone that holds A validates a server certificate from S_new through A and S_old, a phone that holds B through B.
**When.** S has `2 x W + 365` days or fewer left (1275 by default, the date of the `IntermediateCAExpiryWarning` alarm), the manifest lists one Enrollment CA, and the next key generation of S is in `PKI_KMS_CA_KEYS` (otherwise a warning that asks for the next number in `pki.kmsCa.intermediateCaNumbers`; the spare generation 2 is there from the start). The orchestrator starts the highest layer first, so an Intermediate CA that is due goes before an Enrollment CA that is due (the Enrollment CA rotation does not start while S is due).
| Step | Gates | What it does |
|---|---|---|
| `create` | none | S_old issues **A**, valid at most as long as S_old (`kms-ca.sh issue-ca ... 1`). A new Enrollment CA (Cl_new) is signed by S_new, chain `[A, S_old, R]`, stored as a secret, added to the manifest, empty CRL. A is in the manifest as `intermediate-ca-NN-bridge` (server, phone and fed sets). Nothing in use changes. A crashed run continues with A and the secret that it stored |
| `bridge` | none (approval can be required) | The truststores get A and Cl_new. Cl_new becomes the signing keystore with the chain **`[Cl_new, A, S_old, R]`** (`enrollment-chain.pem` is `[A, S_old, R]`). The server certificate stays signed by S_old. Rolling deployment. From now on a new enrolment carries four certificates |
| `admin` | `restart` | The admin certificate is signed by Cl_new (chain Cl_new, A, S_old). Records `bridgeAt`: the time of this step, when the old task has been replaced |
| `cut` | `window` (W after `admin`), `coverage --issued-before bridgeAt`, `approval` | **R issues B** for the S_new key (a Root CA signature: the `RootCASigned` alert fires, expected). Checked: same key and subject as A, chains to R, pathlen 2. B joins the manifest, becomes `intermediate-ca.pem` and `ca.pem` (the FederateCA secret), S_new the current Intermediate CA (`numbers.intermediate`). The server certificate and the admin certificate are re-issued. The keystore of Cl_new gets the chain `[B, R]` (a new version of its secret; `enrollment-chain.pem` is `[B, R]`). Rolling deployment. **Phones that hold only `{S_old, R}` are cut off** |
| `retire` | `window` (W after `cut`), `coverage --issued-before cutAt`, `approval` | S_old, A and Cl_old leave the truststores and the manifest. Cl_old's CRL is deleted and its key destroyed (as in the Enrollment CA rotation). Rolling deployment. The KMS key of S_old is **not** deleted by the container |
Deadlines: `cut` at S_old expiry - (W + 90 days), because a phone on A needs W after the cut to enrol again before S_old expires; `retire` at S_old expiry - 30 days. A deadline opens window and coverage, never the approval. By default `cut` and `retire` need an approval (`pki.kmsCa.rotation.requireApproval`): `cut` cuts off phones that the coverage check cannot see.
**What the phones see.** At the bridge nothing is lost: both kinds of phone accept the server certificate (S_old's). At the cut a phone on `{S_old, R}` stops (the coverage check listed the active ones; `unknown` users with a hand-made data package are not seen by it and are named in the message), a phone on `{A, S_old, R}` and a phone on `{B, R}` accept it. After the cut a phone on A works until A and S_old expire, which is why the deadlines leave W for it to enrol again. The data package truststore (`truststore-phone.p12`) holds `{S_old, A, R}` from the bridge, `{S_old, A, B, R}` after the cut and `{B, R}` after `retire`: **data packages made before the bridge stop working at the cut.**
**Abort.** Before the bridge ran, `pki-rotate.sh abort` undoes `create` (A, Cl_new, its secret with the recovery window, its CRL, the manifest). The S_new key in KMS is not touched. After the bridge it refuses (exit 2): the bridge state is stable (old and new phones both work, the server certificate is still S_old's) and the rotation can wait there; `cut` has its own gates. The cut is idempotent and ordered (B and the trust first, then the switch of `intermediate-ca.pem`, the keystore, the server certificate, the admin certificate): a failure is retried at the next run, and a node that restarts in between has a consistent server certificate.
**The old KMS key.** The task role cannot schedule the deletion of a key, and should not. After `retire` the log says: remove generation N from `pki.kmsCa.intermediateCaNumbers` (CDK then drops the key from the policy of the signer role; keys are retained), and schedule the deletion in KMS with a 30-day window. The scripts need only the generations in `pki-state.json` in `PKI_KMS_CA_KEYS`, so removing the old one breaks nothing. `RotationSpareKeyMissing` asks for the next number.
## Coverage check (`rotation-coverage.sh`)
The window W is time; the coverage check asks TAK Server who is still on the old side ([#171](https://github.com/TAK-NZ/tak-infra/issues/171), slice C). It makes two calls of the TAK Server API with the admin certificate: `/Marti/api/clientEndPoints` (who connected and when) and `/Marti/api/certadmin/cert` (every certificate that TAK Server issued through enrolment, with its dates and the certificate itself).
- An **active user** is connected now or was seen in the last 30 days (`PKI_COVERAGE_ACTIVE_DAYS`, `--active-days`). Its **newest valid certificate** is the one with the latest issuance date that is not revoked and not expired.
- `--issued-before EPOCH` (a rotation that changes what phones trust, #172 and #169): the user is a **straggler** when that certificate was issued before the chain changed.
- `--issuer enrollment-ca-NN` (the removal of an old Enrollment CA, #135): the user is a straggler when that certificate was issued by that CA, that is, no newer CA has issued one.
- An active user **without any valid certificate in the list** is *unknown*: it connects with a certificate that TAK Server did not issue through enrolment (a data package made by hand), so nothing can be said about its chain. Unknown users are reported but do not hold the rotation back (`--unknown-blocks` counts them).
- Output: the number of stragglers (default, what the orchestrator reads), `--list` (a table), `--json`. Any failure (the API does not answer, a call is refused, the answer is not a list) prints nothing and exits 1, and the orchestrator keeps the gate closed.
- A scenario gives its arguments with `<n>_coverage_args <step>`. While a step waits for coverage the orchestrator logs the list and publishes it to the alert topic (`PKI_ALERT_TOPIC_ARN`; the task role may publish to it): who has to enroll again, which step waits, and the day on which the step runs anyway (its deadline). The same set of users is sent once a week, a changed set at once.
## Enrollment CA rotation (`rotation/enrollment.sh`)
The first scenario of the orchestrator ([#135](https://github.com/TAK-NZ/tak-infra/issues/135)). The Enrollment Signing CA (Cl) signs the client certificates that phones get at enrolment and the admin certificate. Its key is a software key in a secret, so it is replaced without KMS: a new Cl is signed by Intermediate CA S (the key in KMS) and TAK Server trusts both until every phone has a certificate from the new one. Phones keep their certificates and their truststore (S and R); nothing changes on a phone except that the next enrolment gives it a certificate from the new Cl.
**When.** The certificate of the current Cl is `enrollmentCaRotationDays` (365) old, the trust manifest lists one Enrollment CA, and S has at least `enrollmentCaRotationDays` + W + 1 days left (the new Cl lives as long as S allows, at most `enrollmentCaDays`, and needs the rotation period plus W). If S has less, the log says that the Intermediate CA has to be rotated first (#172).
| Step | Gates | What it does |
|---|---|---|
| `create` | none | Next number NN (above every number used so far, so a name that is in its recovery window is never reused). A new key and a certificate for `TAK.NZ <Env> Enrollment CA NN`, signed by S, checked against S and R. Stored as the secret `<stack>/TAK-Server/Enrollment-CA-NN`, added to the trust manifest (server set, `trust-certs/enrollment-ca-NN.pem`) and given an empty CRL. Nothing signs with it yet. A run that was interrupted continues with the secret it stored and makes no second key |
| `switch` | none | The server truststore gets both Cl (`trust_apply`). The certificate of the old Cl moves to `trust-certs/enrollment-ca-OO.pem` and the manifest follows. The new Cl becomes the signing keystore (this node's tmpfs, `.enrollmentSecret`, `.numbers.enrollment`, `.names.enrollment`, `enrollment-ca.pem`), `SigningCARotated` is emitted, and a rolling deployment starts. **From here the rotation cannot be aborted.** The other nodes restore the new keystore at their restart |
| `admin` | `restart` | `admin-cert-rotate.sh rotate`: the admin certificate is signed by the new Cl. It waits for a task that started after the switch, because only that task trusts and signs with the new Cl (the old admin certificate is revoked after its grace period, #204) |
| `retire` | `window`, `coverage` (`--issuer enrollment-ca-OO`), `approval` | The old Cl leaves the truststores and the manifest, its CRL and database are deleted, **its key is destroyed**, a rolling deployment starts. Every certificate it issued stops working. Deadline: 30 days before the old Cl expires (window and coverage open then; the approval does not) |
The wait before `retire` is W = 455 days since the `admin` step, the time a phone needs to get a certificate from the new Cl by its yearly renewal, and the coverage check lists the active users that have not. `pki-rotate.sh approve enrollment retire` releases the last step.
**Destroying the key.** A generation of 2 or more is a secret that the rotation created, and it is deleted with `DeleteSecret` and a **recovery window of 30 days**: for a month it can still be restored (`aws secretsmanager restore-secret`). The task role may delete only `<stack>/TAK-Server/Enrollment-CA-NN` (not the secret of generation 1) and only with a recovery window of 30 days or more; `ForceDeleteWithoutRecovery` is denied. Generation 1 is the secret that CDK creates for the stack: it stays, and its value is overwritten twice with a text, so that the current and the previous version no longer hold the key. The first version, which then has no staging label, is deprecated: Secrets Manager removes it at its own pace, and it can be read only by its version ID (which the task role cannot list). To remove it at once, delete the secret by hand. The old key is also needed until `retire` to sign the CRL entries of the old admin certificates; after it nothing needs it.
**Abort.** `pki-rotate.sh abort` before the switch undoes `create` completely (manifest, CRL, file, secret with the recovery window; the number is not reused). After the switch it refuses (exit 2): the new Cl signs and phones may hold its certificates, so the rotation goes on to `retire`. A rotation that must end sooner than that is a manual operation (`pki-trust.sh`, `revoke-cert.sh`).
**Checked on the dev-test stack (TAK Server 5.8, a real rotation with `enrollmentCaRotationDays=1`, window 2 days):** `create` and `switch`, a rolling deployment, then the `admin` step from the first daily run of the new task (new admin certificate signed by Enrollment CA 02, accepted by the API); `retire` after window, coverage (real API: the straggler list went to the alert topic) and approval. Before `retire` both Enrollment CAs are accepted on 8089; after it a certificate from Enrollment CA 01 is refused on 8089 (`alert internal error`, as for a self-signed one) and on 8443 (`certificate unknown`), certificates from Enrollment CA 02 are accepted, a certificate of CA 02 that was revoked with `revoke-cert.sh` is refused (`certificate revoked`), the secret of generation 1 holds only the text, and the task role may delete a generation secret with a recovery window of 30 days but not with 7 days, without a window, with `--force-delete-without-recovery`, or the secret of generation 1.
**What happens to a client.** A certificate from the old Cl works until `retire` (the server truststore holds both). A phone that enrolls after the switch gets a certificate from the new Cl, which chains to S and R and passes the same checks (checked on the dev-test stack: both accepted, the old one refused after `retire`, probe on port 8089 with `openssl s_client -tls1_2`, as in #204).
## Admin certificate rotation (`admin-cert-rotate.sh`)
The admin client certificate (`admin.pem`, `admin.key`, `admin.p12`) is rotated automatically on stacks with the first-boot PKI ([#132](https://github.com/TAK-NZ/tak-infra/issues/132)). The same daily loop as for the server certificate runs `admin-cert-rotate.sh check`; it rotates at `pki.kmsCa.validity.adminCertRenewDays` (default 60) or fewer days left. `admin-cert-rotate.sh rotate` rotates at once. The admin certificate is used by the container health check (`admin.pem` and `admin.key`), by the admin elevation at start (`certmod -A admin.pem`) and, through the secret `<stack>/TAK-Server/Admin-Cert`, by TAKTeamManager, CloudTAK and other services.
Under the cluster lock `admin-cert-rotation`:
1. A new key for `CN=admin`, signed by the Enrollment CA (its key is the software key that `start-tak.sh` restores from Secrets Manager into tmpfs, so it never touches the EFS). Validity `adminCertDays` (default 365), capped to what the Enrollment CA has left; if that is not more than the renewal threshold the rotation stops and says to rotate the Enrollment CA first (#135).
2. Built and checked in tmpfs: chain to R, S and Cl, key against certificate, CN, and that `admin.p12` (compat3des or aes256, as configured) and `admin.key` open with the keystore password.
3. **Registered before any file changes**: `UserManager.jar certmod -A` for the new certificate, `certmod -s` must list it as `ROLE_ADMIN` with the new fingerprint, and one call to the TAK Server API (`/Marti/api/certadmin/cert`) with the new certificate must answer 200. A failure here changes nothing on the EFS and registers the current certificate again.
4. Swap of the three files: marker, `.prev` copies, one atomic rename per file, the same checks on the installed files. A failure restores the `.prev` copies and registers the old certificate again; an interrupted swap is restored at the next run.
5. The secret is updated with the file hash as request token (the same token `start-tak.sh` uses, so the next start sees "unchanged"). If that fails the new files stay, `AdminCertRotationFailed` is emitted, `adminSecretPending` is set in `pki-state.json`, and the next daily check tries the secret again.
6. `pki-state.json` gets the new `notAfter.admin`, `AdminCertRotated` is emitted. **No restart**: the health check reads the files on every call, and TAK Server looks the user up when a request arrives.
`pki-state.json` keeps the replaced certificates in `adminPrevious` (serial, SHA-256 fingerprint, `notAfter`, issuer, `replacedAt`), so that a CRL for the Enrollment CA ([#204](https://github.com/TAK-NZ/tak-infra/issues/204)) can revoke them later.
The `.prev` copies hold the previous admin key. They are deleted `pki.kmsCa.validity.adminCertGraceDays` (default 7) after the rotation. That is the window for a rollback and for the services to pick up the new secret (TAKTeamManager refreshes it every 24 hours).
**What this does not do: revoke the old admin certificate.** TAK Server finds the admin user by the CN `admin` of any certificate that its truststore accepts (checked on the dev-test stack: a new certificate with CN `admin` from the same CA was accepted as administrator before it was registered, and the old one still works after `certmod -A` of the new one; `certmod -A` only replaces the stored fingerprint). No CRL is configured, and the certadmin revoke API only knows certificates that TAK Server issued itself, which the admin certificate is not. The old certificate therefore works until its own `notAfter`, or until its issuer is removed from the truststore (an Enrollment CA rotation, #135). If an admin key is compromised, rotate the Enrollment CA, do not wait for this script. Revoking one certificate needs a CRL for the Enrollment CA, which is #204. `certmod -D` is not an option: it deletes the user `admin` and so every admin certificate.
## Metrics and alarms (`cert-metrics.sh`)

One helper for all certificate work ([#129](https://github.com/TAK-NZ/tak-infra/issues/129)). Metrics go to the CloudWatch namespace `TAK/Certificates` with the dimension `Stack=<stack name>`; the alarms (created with `pki.kmsCa`) fire at a value of 1 and treat missing data as fine, so an alarm whose emitter is not built yet stays in OK.

From a script: `/opt/tak/scripts/cert-metrics.sh emit <MetricName> [value] [Dimension=Value ...]`, or `source` it with `CERT_METRICS_SOURCE_ONLY=1` and call `emit_metric`. It refuses names that are not in the table (a typo would feed no alarm), validates the dimensions, and never fails the caller when CloudWatch cannot be reached.

| Metric | Alarm | Severity | Emitted by |
|---|---|---|---|
| `RootCAExpiryWarning` | daily maximum >= 1 | alert | `cert-metrics.sh check-expiry`: Root CA expires in 730 days or less |
| `IntermediateCAExpiryWarning` | daily maximum >= 1 | alert | `check-expiry`: Intermediate CA expires in 1275 days (2W + 1 year) or less |
| `CAExpired` | daily maximum >= 1 | critical | `check-expiry`: Root, Intermediate or Enrollment CA has expired |
| `RootCASigned` | every `kms:Sign` with a Root CA key | alert | the EventBridge rule of #136 (CloudTrail), not a metric |
| `CertbotRenewalFailure` | 5 minute sum >= 1 | alert | `certbot-renew.sh` and `letsencrypt-request-cert.sh` (#130, `docs/LETSENCRYPT.md`) |
| `TakServerCertRotated` / `TakServerCertRotationFailed` | 5 minute sum >= 1 | info / alert | `server-cert-rotate.sh` (#131, below) |
| `AdminCertRotated` / `AdminCertRotationFailed` | 5 minute sum >= 1 | info / alert | `admin-cert-rotate.sh` (#132, below) |
| `SigningCARotated` | 5 minute sum >= 1 | info | `rotation/enrollment.sh`, the switch step (#135, above) |
| `IntermediateCARotationPhase` (`Phase=bridge`, `cut`, `retire`) | 5 minute sum >= 1, one alarm per phase | info | #172 |
| `RootCARotated` | 5 minute sum >= 1 | info | #169 |
| `RotationCoverageStragglers` | 5 minute sum >= 1 | alert | #171 |

`check-expiry` reads `root-ca.pem`, `intermediate-ca.pem` and `enrollment-ca.pem` in the files directory and emits 0 or 1 for the three metrics every time, so the alarms return to OK and "no data" is not mistaken for "fine". It does nothing on a stack without `pki-state.json` (a PKI from the old scripts). `start-tak.sh` runs it 60 seconds after the start and then every 24 hours. The thresholds are `PKI_ROOT_WARN_DAYS` (730) and `PKI_INTERMEDIATE_WARN_DAYS` (1275).

Three SNS topics by severity: alert, critical and info. `pki.kmsCa.alertEmail` subscribes the alert and critical topics, `pki.kmsCa.infoEmail` the info topic; without an address the topics exist and you subscribe to them yourself. The Root CA signing alert of #136 publishes to the alert topic.

## Retiring a key

When a rotation is complete (#169, #172), schedule the old key for deletion with the full window:

```bash
aws kms schedule-key-deletion --key-id alias/tak-nz-try-intermediate-ca-01 --pending-window-in-days 30
```

The task role has no permission to do this. Afterwards remove the number from `rootCaNumbers` / `intermediateCaNumbers`; CloudFormation retains the key either way.
